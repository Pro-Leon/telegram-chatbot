## 7. Offer Correlation Conclusion

**DEFINITIVE ANSWER**: Fangate does NOT provide a deterministic purchase → offer correlation mechanism.

Evidence:
- The word "offers" does not appear in any official documentation page
- The webhook delivery payload contains: `transaction_id`, `buyer_email`, `seller_earning`, `currency`, `product_id`, `media_ids`, `set_price`
- There is NO `offer_id`, `checkout_id`, `order_id`, `session_id`, `external_reference`, `reference`, `metadata`, or `price_link_id` field in the documented webhook payload
- The only available correlation is `creator_id + product_id`
- The repository's `attribute_purchase_from_webhook()` correctly uses this limited correlation with an ambiguity guard (fail-closed when multiple candidates exist)

**Current approach is the best possible given the API constraints.** No stronger mechanism exists in the documented API.

## 8. Media Contract Conclusion

**DEFINITIVE ANSWER**: Fangate's officially supported media lifecycle is:

1. **Upload** → upload session → `POST /api/media` → library item (status: pending)
2. **Link to product** → `POST /api/products/{product}/media` with `{"media_ids": [101, 102]}`
3. **Detach from product** → `DELETE /api/products/{product}/media/{media_id}`
4. **Delete from library** → `DELETE /api/media/{media_id}` (fails if still linked)
5. **Product response** → `media[]` array via n:m `product_media` pivot
6. **Webhook** → `data.media_ids` array of `m_{id}` strings

The repository's `upload_product_media()` implements a **legacy direct-upload** path (multipart file to product endpoint), not the current library-first flow. This may still work as backward compatibility but is NOT the documented current approach.

Missing from repository:
- `DELETE /api/products/{product}/media/{media_id}` (detach)
- `GET /api/media` (library list)
- `POST /api/media` (library create)
- `DELETE /api/media/{media_id}` (library delete)
- `POST /api/media/bulk` (bulk upload sessions)

## 9. Webhook Contract Conclusion

**DEFINITIVE ANSWER**: The official webhook contract is:

**Registration**: `POST /api/webhooks` with `{url, events[], include_set_price?}` → `201` with `{...resource, secret}` (shown once)
**List**: `GET /api/webhooks` → array without secret
**Update**: `PATCH /api/webhooks/{id}` with partial `{url?, events?, include_set_price?, is_active?}`
**Delete**: `DELETE /api/webhooks/{id}` → removes webhook + delivery history

**Delivery**: `POST` to registered URL with:
- `Content-Type: application/json`
- `X-Fangate-Signature: sha256={hmac-sha256}` (HMAC-SHA256 of raw body)
- `X-Fangate-Delivery-Id: {uuid}` (idempotency key)
- Body: `{event, timestamp, data: {transaction_id, buyer_email, seller_earning, currency, product_id, media_ids[], set_price?}}`

**Retry**: Up to 3 attempts, backoff 1 min → 5 min → 30 min
**Supported events**: `payment.successful`, `payment.failed`, `payment.pending`
**Auth**: Creator Sanctum bearer token or API key with `api-key:webhooks.manage`

The repository's implementation MATCHES this contract exactly across all 5 webhook endpoints (client, service, and dashboard layers).

**POST /webhooks/test**: UNVERIFIED — not documented. The repository implements it (client.py:569) but there is no official evidence it exists.
